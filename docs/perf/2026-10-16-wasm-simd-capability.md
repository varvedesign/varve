# WASM SIMD capability, artifact selection, and measured effect threading (2026-10-16)

Dated audit + measurement. Absolute times are indicative: the machine was under
a load average of ~20-26 from other sessions for every run. Ratios come from
interleaved A/B in one process (or from the kernels' own scalar/bounded pair).

## What changed

### 1. The capability probes were invalid modules (defect, fixed)

`capabilityReport.ts` had two probe byte arrays. Both were malformed:

- SIMD probe: `... 65 0, fd 15, fd 15` applied `i8x16.splat` (opcode 15) to the
  `v128` produced by the previous `i8x16.splat`, which is a type error.
- Threads probe: memory section declared size 5 with 4 bytes of payload, so the
  validator read the next section id as a limit byte.

`WebAssembly.validate` therefore returned `false` for both on *every* engine.
The report has been claiming "WASM SIMD: no / threads unavailable" on hardware
that supports both. Reproduced directly:

```text
$ node -e "... WebAssembly.validate(new Uint8Array(oldSimd)) ..."
old simd false
threads decl false
new simd true
```

Both probes now live in `@varve/engine` (`runtimeCapabilities.ts`) as validated
bytes: a `i32x4.add` module and a shared-memory module with one
`i32.atomic.load`. `runtimeCapabilities.test.ts` validates them against the real
engine, which is the regression: it fails on the previous bytes.

### 2. Artifact selection is evidence-based (not file-presence-based)

Before: the loader always tried `varve_wasm_simd_bg.wasm` first. On an engine
without SIMD that meant a ~1.1 MB fetch, compile and failed instantiation on
every session before falling back to the baseline artifact, and no diagnostics
reported what actually ran.

After:

- `wasmArtifactCandidates()` returns `['simd','baseline']` only after the engine
  validated a `v128` module; otherwise only `['baseline']`, and the fetch is
  never attempted.
- `getWasmEngineAttribution()` reports `artifact`, `version`, the skipped
  candidate and each failed stage (`head` / `glue` / `instantiate`) with a
  bounded reason.
- `setWasmArtifactPreference('baseline' | 'auto')` is the A/B seam.
- The colour loader records the same attribution. It stays baseline-only
  because the colour artifact contains no vector instructions (below); adding a
  `+simd128` colour build would be a label with no work behind it.

### 3. Threads are reported truthfully

`threadsUsable` requires all three of: the engine validates shared memory + an
atomic instruction, a `SharedArrayBuffer` can actually be constructed, and
`crossOriginIsolated` is true. On WebKitGTK 2.52 the shared buffer is absent
even with correct COOP/COEP, so a threaded WASM artifact would not run there.
A threaded `wasm32-unknown-unknown` build also needs nightly `-Z build-std`,
which this pinned stable toolchain cannot do. The web path is therefore
single-threaded WASM (or the TS fallback); the native path uses threads.

## 4. Artifact inspection

```text
$ node scripts/quality/verify-wasm-simd.mjs
varve_wasm_bg.wasm: 0 vector instructions -> verified (baseline claim: must be 0)
varve_wasm_simd_bg.wasm: 6126 vector instructions -> verified
varve_colour_bg.wasm: 0 vector instructions -> verified (baseline claim: must be 0)
OK: 3 artifact(s) inspected; SIMD claims match the bytes.
```

| Artifact | Bytes | `v128` instructions | Claim |
|---|---|---|---|
| `varve_wasm_bg.wasm` | 1,136,808 | 0 | baseline |
| `varve_wasm_simd_bg.wasm` | 1,146,397 | 6,126 | SIMD |
| `varve_colour_bg.wasm` | 526,600 | 0 | baseline |

A fresh rebuild from the current tree (`wasm-pack --out-dir /tmp/opencode/wasm-build`,
engine 0.5.1, `sha256 a58aead9…` / `7ca1bee7…`) produced the same byte sizes and the
same 0 / 6,126 split, so the inspection is not an artifact of an old build. The
in-tree binaries hash differently (`47382c17…` / `7288f46b…`), which is expected
for a repack, not a source difference.

The SIMD artifact is genuinely vectorized. Top instruction mix:
`i32x4.extract_lane` 305, `i8x16.replace_lane` 237, `i32x4.add` 186,
`i8x16.shuffle` 159, `i32x4.mul` 121, `i16x8.extend_low_i8x16_u` 114,
`f64x2.mul` 29. The shipped module has no name section, so per-function
attribution is not available from the binary.

`just verify-wasm-simd` exits `1` when a claim and the bytes disagree and `2`
(`UNVERIFIED`) when `llvm-objdump` is missing. It never converts an unrun check
into a pass.

## 5. Output parity and A/B on the exported work

`just bench-wasm` loads both artifacts through their own wasm-bindgen glue (the
same bytes a browser fetches), runs them on synthetic scenes, and asserts
byte equality before timing.

```text
$ node scripts/quality/bench-wasm-artifacts.mjs --reps 20
node v22.23.2 / V8 — wasm engine 0.5.0
nodes |  ir bytes | baseline p50 | simd p50 | speedup | identical
  200 |     45495 |        4.679 |    4.491 |    1.04x | true
  600 |    136627 |        6.975 |    7.067 |    0.99x | true
 2000 |    456945 |       24.908 |   23.088 |    1.08x | true
```

- IR JSON is byte-identical at every size; hit-test indices agree.
- Contour trace at 768×768 is byte-identical and ~1.0x (round medians 0.88x to
  1.07x, i.e. inside load noise).
- The exported path includes serde JSON parse + serialize, which dominates the
  work; a kernel-level SIMD gain is not visible through that boundary.

The isolated rebuild from the current source tree reproduces the result at
engine 0.5.1:

```text
$ VARVE_WASM_DIR=/tmp/opencode/wasm-build node scripts/quality/bench-wasm-artifacts.mjs --reps 20
nodes |  ir bytes | baseline p50 | simd p50 | speedup | identical
  200 |     45495 |        3.629 |    3.752 |    0.97x | true
  600 |    136627 |        6.777 |    6.707 |    1.01x | true
 2000 |    456945 |       22.245 |   22.371 |    0.99x | true
```

The IR byte counts are identical to the in-tree run (`45495` / `136627` /
`456945`), which is a second, independent confirmation that both artifacts
produce the same output.

**Conclusion: SIMD is real in the artifact but not a measured acceleration for
any exported canvas path. No SIMD speedup is claimed.** The audit also found no
raster pixel kernel in the WASM surface (IR build, hit-test, trace, media probe
only), so `+simd128` cannot affect canvas rasterization today.

## Ledger (source → finding → evidence → decision → regression → result)

| Source / date / version | Bounded finding | Varve evidence | Decision | Regression | Measured / visual result |
|---|---|---|---|---|---|
| `capabilityReport.ts` probe constants, 2026-10-16 | Both WASM probes were structurally invalid, so SIMD and threads were reported as unsupported on every engine | `WebAssembly.validate` returns `false` for both old byte arrays and `true` for the replacements (reproduced in Node, quoted above) | Move the probes into `@varve/engine` as validated bytes; one source of truth for loader, report and diagnostics | `runtimeCapabilities.test.ts` -> "runs a real v128 validation on this host" fails on the old bytes | Probes validate true; the report no longer prints a constant |
| `justfile` `+simd128` build, 2026-10-16 | The SIMD artifact is genuinely vectorized (the flag is not a no-op) | 6,126 `v128` instructions in `varve_wasm_simd_bg.wasm`, 0 in both baseline artifacts, on two independent builds | Keep the artifact, but verify it mechanically instead of asserting it | `just verify-wasm-simd` exits 1 on a claim/bytes mismatch, 2 when unverified | Exit 0 with all three artifacts present |
| Exported engine work (IR build, hit test, trace), engine 0.5.0 + 0.5.1 | SIMD is not measurably faster through the JSON boundary, and must not be claimed as acceleration | Interleaved A/B, byte-identical outputs at 200/600/2000 nodes and 768x768 trace; 0.97x-1.08x | No SIMD rendering claim; no SIMD colour artifact (its workload has 0 vector instructions) | `just bench-wasm` fails on any output mismatch between artifacts | Identical IR bytes (45495/136627/456945) and ~1.0x on both builds |
| `wasm32-unknown-unknown` + WebKitGTK 2.52, 2026-10-16 | A threaded WASM build cannot ship on this toolchain, and could not run on the primary Linux webview even if it did | Stable std for this target has no atomics; `std::thread::spawn` panics; WebKit GLib ports only enabled `JSC_useSharedArrayBuffer` for isolated origins in September 2026 (after 2.52) | Web stays single-threaded; `threadsUsable` reports the three prerequisites instead of a guess | `runtimeCapabilities.test.ts` pins that a missing `SharedArrayBuffer` or isolation yields `threadsUsable: false` | No threaded artifact built; diagnostics say "unavailable" for the right reason |
| External analogue: filmcraft#1836 (proposed, 2026-10-14) | A wasm SIMD128 conversion path is claimed bit-identical to scalar, verified by a parity test rather than a benchmark | Not reproducible here (different product); the claim shape matches this repo's approach | Adopt the same shape: parity first, then timing, and never the reverse | This document's harness asserts byte equality before reporting any ratio | Varve's parity holds; its timing shows no gain |

## Decisions

1. Keep the shared capability probe as the single source of truth; never report
   SIMD/threads from file presence or a build flag.
2. Select the SIMD artifact only after `WebAssembly.validate` accepts `v128`;
   always keep the baseline artifact as a real fallback.
3. Do not add a SIMD colour artifact (0 vector instructions in its source
   workload today).
4. Do not claim SIMD rendering acceleration. The measured parallel win is the
   native row-band path (D6).
5. Keep the automated verifier and A/B harness so a future SIMD kernel can be
   checked, not asserted.

## Limits (explicitly unverified)

- The A/B ran in Node/V8, **not** WebKitGTK or WKWebView. Browser numbers may
  differ; no browser certification is implied.
- Artifacts are local, gitignored builds. The verification is reproducible with
  `just wasm-build && just verify-wasm-simd && just bench-wasm`, not by
  inspecting a committed binary.
- No threaded WASM path was built or run: it is unreachable on stable Rust and
  unusable on WebKitGTK 2.52.
- The WASM surface has no raster kernel, so no raster pixel result is claimed.
- The native effect numbers were taken on one 4-core laptop under heavy external
  load; they corroborate D6's direction, not its exact ratios.

## Reproduction

```bash
just wasm-build            # baseline + SIMD + colour artifacts (gitignored)
just verify-wasm-simd      # disassembly claim check; exit 2 = unverified
just bench-wasm            # parity + interleaved A/B
cargo run --release -p varve-effects --example effect_cost 1024
```

For an isolated build that does not disturb the shared `public/wasm` directory:

```bash
cd crates/varve-wasm
wasm-pack build --target web --out-dir /tmp/varve-wasm --out-name varve_wasm
RUSTFLAGS="-C target-feature=+simd128" \
  wasm-pack build --target web --out-dir /tmp/varve-wasm --out-name varve_wasm_simd
cd ../varve-colour
wasm-pack build --target web --out-dir /tmp/varve-wasm --out-name varve_colour -- --features wasm
VARVE_WASM_DIR=/tmp/varve-wasm just verify-wasm-simd
VARVE_WASM_DIR=/tmp/varve-wasm just bench-wasm
```

`verify-wasm-simd` exits `2` (UNVERIFIED) if any claimed artifact is missing,
so an isolated directory must contain all three or the colour claim is reported
as unchecked rather than passed.
