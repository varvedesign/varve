## Per-topic notes

### 1. Common responsive failures in desktop-first apps
- Fixed-width side rails plus a min-width shell: the shell keeps its desktop width and the page gets
  horizontal overflow, or the sidebar clips. Wider than 899 px there is currently no rule at all in
  Varve (next existing values are 900 and 980), so 900-980 is an unmanaged band.
- Absolute/fixed toolbars: 19 CSS files use position: fixed. On short viewports (1366x768 laptop
  with browser chrome, or iPad landscape at 1024/820 px height minus Safari UI) fixed chrome can
  cover the canvas and become unclickable underneath.
- Overflow clipping: overflow: hidden on panel containers hides the symptom in one panel and moves
  it to another; clipping is also how "missing toolbar on rotate" bugs appear.
- Breakpoint gaps: with 20 distinct widths and no tokens (899/900/640/480/768/720/680/520/980/860...)
  any new rule can land between two existing ones and produce an unstyled band.
- Desktop-first assumptions that break quietly: hover-only reveals, 24 px icon buttons, tables with
  min-width, dialogs sized in px, and focus outlines removed for mouse users.
- Mobile-first is the documented inversion (start single column, add columns at wider widths):
  https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design

### 2. The 13-inch iPad / square-viewport breakpoint trap
Exact CSS viewports (points = CSS px, physical / 2 on these devices):
- iPad Pro 12.9-inch (5th/6th gen): 2732x2048 physical -> 1366x1024 landscape, 1024x1366 portrait.
- iPad Pro 13-inch (M4): 2752x2064 physical -> 1376x1032 landscape (arithmetic from Apple's
  published resolution; verify against a live unit before hardcoding).
- iPad (10th gen) / iPad Air 11-inch: 2360x1640 -> 1180x820 landscape, 820x1180 portrait.
- Laptop 1366x768 at 100% scaling is 1366x768 CSS; at 125% Windows scaling it is ~1093x614 CSS.
- 14-inch MacBook Pro: 3024x1964 native, default "looks like" 1512x982.
Sources: https://www.ios-resolution.com/ (logical 1024x1366 and 820x1180 rows),
https://www.apple.com/ipad-pro/specs/, https://www.apple.com/macbook-pro/specs/.
- Why width-only fails: against Varve's 899 px cutoff, a 10.9/11-inch iPad is "mobile" in portrait
  (820) and "desktop" in landscape (1180); a 12.9/13-inch iPad is "desktop" in both orientations
  (1024/1366) even though it is held. Height does not rescue it: 1024/1032 px is taller than a
  1366x768 laptop. Aspect ratio does separate them: 1.33 (4:3 tablet) vs 1.54-1.78 (laptops).
- Split View and Slide Over put the app below any width tier: half of 1366 is ~683 px, a third
  ~455 px, half of 1180 is ~590 px; Slide Over is a narrow phone-class column. Any ">= 900 means
  desktop" rule collapses there, which is why the tier must be input-aware, not width-only.
- Apple's own guidance is explicit: determine layout from size classes, not device type or
  orientation ("a device's orientation and type ... aren't useful for making layout decisions
  because they don't provide your app with information about how much space is available"):
  https://developer.apple.com/design/human-interface-guidelines/layout
- Orientation change re-evaluates media queries; JS breakpoint state read once at mount goes stale.
  Use matchMedia listeners, not a one-time innerWidth read.

### 3. Hover dependency
- Semantics: hover:hover means the primary input can conveniently hover; hover:none includes devices
  that emulate hover with an awkward long tap. pointer:coarse means a finger-class device;
  pointer:fine means a mouse-class device. MDN: https://developer.mozilla.org/en-US/docs/Web/CSS/@media/hover ,
  https://developer.mozilla.org/en-US/docs/Web/CSS/@media/pointer
- Gotchas: a touch laptop with a trackpad reports hover:hover/pointer:fine (primary pointer is the
  trackpad), so hover-only UI stays "reachable" in testing while being unreachable on pure touch.
  Conversely iPad + trackpad misreported hover:none/pointer:coarse until WebKit fixed it, so the same
  iPad reports differently by OS version and attachment state:
  https://bugs.webkit.org/show_bug.cgi?id=209292 (reported 2020-03-19, RESOLVED FIXED).
- Emulated hover in DevTools (device toolbar) does not reproduce real pointer transitions; test on
  hardware or use pointer events with pointerType.
- Compat-data documents that hover/pointer values are inaccurate on Android, ChromeOS, iOS and
  Windows and that the spec leaves "primary pointing device" determination to the UA:
  https://github.com/mdn/browser-compat-data/issues/24451
- Practical rule for Varve: hover reveals are additive. Every action reachable only by hover must
  also exist on focus-visible or a tap path; tooltip-only actions fail both touch and keyboard.

### 4. Mobile viewport units
- The 100vh bug, stated precisely: vw/vh do not change when dynamic browser toolbars expand or
  retract, so "elements sized to be 100vh tall will bleed out of the viewport" and "100vh on mobile
  is too tall on load": https://web.dev/blog/viewport-units
- Definitions: large viewport (lv*) assumes retracted UA UI, small viewport (sv*) assumes expanded UA
  UI, dynamic (dv*) is clamped between them. All are stable unless the viewport itself resizes.
  Ship status in that article: Chrome 108, with Safari and Firefox already supporting them.
- When each is right: svh for shells/dialogs that must fit with the address bar visible (the safe
  default for the editor chrome); dvh for full-bleed surfaces that should grow as UI retracts;
  lvh only for deliberately edge-to-edge content that may be partially hidden. Minimum for a
  guaranteed-visible action area: svh.
- Virtual keyboard: it shrinks the visual viewport, not the layout viewport; meta viewport
  interactive-widget selects resizes-visual (default), resizes-content, or overlays-content, and
  "when the viewport gets resized, the initial containing block also gets resized, thereby affecting
  the computed size of viewport units":
  https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport
- visualViewport API gives width/height/scale/offset and resize/scroll events, which is how you keep
  a focused input or floating palette visible: https://developer.mozilla.org/en-US/docs/Web/API/Visual_Viewport_API
- Pinch-zoom changes visualViewport.scale while the layout viewport is unchanged - this is also the
  signal a canvas app needs to distinguish "user zoomed the page" from "we scaled the canvas".

### 5. Touch target sizing
- WCAG 2.2 SC 2.5.8 Target Size (Minimum), Level AA: "The size of the target for pointer inputs is
  at least 24 by 24 CSS pixels", with five exceptions (spacing where a 24 CSS px diameter circle per
  undersized target does not intersect another, equivalent control, inline, user-agent control,
  essential). The stricter 2.5.5 (Enhanced) is 44x44 CSS px (Level AAA):
  https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html
- Apple HIG: "a button needs a hit region of at least 44x44 pt - in visionOS, 60x60 pt":
  https://developer.apple.com/design/human-interface-guidelines/buttons
- Android guidance is 48x48 dp, but no authoritative Google page could be machine-read this session
  (developer.android.com and support.google.com return JS shells; the string 48dp was not in the
  returned HTML). Treat 48 dp as platform guidance to confirm manually before citing in the plan:
  https://support.google.com/accessibility/android/answer/7101858 (page exists, content unverified).
- touch-action: manipulation keeps panning and pinch-zoom but disables double-tap-to-zoom, and MDN
  states this "removes the need for browsers to delay the generation of click events" - the modern
  answer to the historical 300 ms tap delay:
  https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action
- Consequence for Varve: dense toolbar buttons (roughly 24-28 px today) clear 2.5.8 only by spacing;
  on touch they need 44 px hit regions via padding/pseudo-elements without changing visual density.
- Thumb-zone reachability is a practitioner heuristic, not a normative source; no authoritative
  numeric citation was found this session, so the plan should treat bottom-anchored primary actions
  as a design decision to be tested, not as a compliance claim.
- Rage-tap detection is likewise an instrumentation heuristic; the only sourced mechanism here is
  double-tap zoom suppression via touch-action.

### 6. iPadOS desktop-class browsing
- Safari 13 release notes: "Added Desktop-class Browsing to Safari for iPad. Safari for iPad displays
  the same desktop websites as Safari for macOS, and provides the same capabilities", plus "Added
  automatic support for Fast Tap to desktop websites on iPad":
  https://developer.apple.com/documentation/safari-release-notes/safari-13-release-notes
- The same notes record a behavior change that hides responsive bugs: "Changed the default behavior
  on iPad for wide web pages with responsive meta-tags that require horizontal scrolling. Pages are
  scaled to prevent horizontal scrolling and any text is resized to preserve legibility." A too-wide
  layout on iPad may look "fine" because Safari scaled it, not because it reflowed.
- Detection pitfalls: UA sniffing is explicitly discouraged ("very hard to do reliably, and is often
  a cause of bugs"), and feature detection is the documented alternative:
  https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Browser_detection_using_the_user_agent
- "Request Desktop Website" is a per-site user toggle, so the same iPad can send either a mobile or
  a desktop profile; combined with desktop-class browsing by default, server-side UA gates are not a
  reliable tier signal. (Apple's user-guide page for this toggle could not be fetched this session -
  bot challenge - so the plan should verify the exact toggle wording on device.)
- Do not detect touch by "narrow width and touch events". Use pointer/hover media features as hints,
  pointerType on real events as truth, and keep the layout tier independent of both.

### 7. Safe areas and notches
- WebKit: env() exposes safe-area-inset-left/right/top/bottom; viewport-fit defaults to auto
  (automatic insetting) and viewport-fit=cover makes the page lay out to the full screen; insets are
  non-zero in landscape where the sensor housing is:
  https://webkit.org/blog/7929/designing-websites-for-iphone-x/
- Pattern: padding-left: max(12px, env(safe-area-inset-left)) so normal margins survive where the
  inset is 0 (portrait), and the larger inset wins in landscape. Same blog.
- env() supports a fallback argument, which matters for older WebKitGTK/WKWebView builds:
  https://developer.mozilla.org/en-US/docs/Web/CSS/env
- MDN viewport meta: viewport-fit cover "is highly recommended to use the safe area inset variables"
  to keep content on screen; values are auto, contain, cover:
  https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport
- Installed/standalone PWA: not separately documented in the sources fetched; the plan should treat
  "test in standalone display mode with viewport-fit=cover" as a required manual check rather than a
  sourced guarantee.
- Desktop Tauri windows have no notch insets in CSS terms; the web build and Astro site are the
  surfaces that need this.

### 8. Canvas / design-tool specific issues
- Pointer events unify mouse, pen and touch; pointerType distinguishes them and pressure/tilt/contact
  geometry are available, which is what a precision tool needs instead of mouse events:
  https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events
- Capture is mandatory for drag selection: setPointerCapture routes subsequent events to the capture
  element until release or pointercancel (Baseline widely available since July 2020):
  https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture
- Gesture takeover: the browser fires pointercancel when it claims a gesture for scrolling/zooming, so
  touch drags must handle cancel and roll back partial selection state (same page).
- Pinch-zoom vs browser zoom is a real conflict: touch-action: none on the canvas disables browser
  pan/zoom, which is what drawing needs but removes the user's ability to magnify. Keep touch-action
  scoped to the canvas element, provide our own two-finger pan/zoom, and never disable zoom on the
  chrome around it. MDN lists none/pan-x/pan-y/pinch-zoom/manipulation semantics:
  https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action
- Precision input: getCoalescedEvents() returns the sub-frame pointer samples merged into a
  pointermove; it is secure-context only and MDN marks it "Limited availability" (not Baseline), so
  it is an enhancement for stroke quality, never the only path:
  https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getCoalescedEvents
- Coordinate discipline: pointer events carry client coordinates in CSS px; a canvas backing store is
  in device px (CSS px x devicePixelRatio). All hit-testing and threshold constants stay in CSS px,
  matching the repo rule that screen-space thresholds stay in CSS pixels.
- Two-finger gestures on iPad trackpads arrive as wheel/pointer events, not touch; the canvas needs a
  wheel path (pan/zoom) in addition to touch.

### 9. Container queries vs media queries
- Support: Chrome 105 (2022-09-02), Safari 16 (2022-09-12), Firefox 110 (2023-02-14); Baseline
  "widely available" since 2025-08-14; ~31.7% of page loads per Chrome Platform Status:
  https://web-platform-dx.github.io/web-features-explorer/features/container-queries/
- Mechanics: declare container-type: inline-size (or size) on a wrapper, then @container (width > N)
  styles descendants based on the nearest containment context; the same card can be reused in
  different widths without knowing where it is placed:
  https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_containment/Container_queries
- MDN marks container-type Baseline "widely available" (available since February 2023):
  https://developer.mozilla.org/en-US/docs/Web/CSS/container-type
- When they beat viewport media queries: sidebar/inspector panels that can be docked, floating or
  collapsed; home file cards that appear in a grid, a list and a picker; dialogs reused as full-screen
  sheets on phones. Those components should respond to their own width, not the window's.
- When media queries remain correct: app-shell tiering, orientation, pointer/hover capability, height
  bands, safe-area and reduced-motion. Container queries cannot query pointer type or viewport size.
- Caveat for desktop packaging: container query support depends on the WebKit in the runtime
  (WKWebView on macOS, WebKitGTK on Linux). Verify the packaged WebKit version before relying on a
  query; no authoritative WebKitGTK version table was fetched this session.

### 10. Tauri 2 / WebKitGTK / macOS WKWebView quirks
- Window sizes in tauri.conf.json are logical pixels, not device pixels: the schema documents
  minWidth/minHeight/maxWidth/maxHeight as "in logical pixels", with width default 800 and height
  default 600: https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-schema-generator/schemas/config.schema.json
  Varve currently sets 1280x800 with minWidth 900 / minHeight 600, so the desktop app cannot be
  resized into any tier below 900x600.
- Zoom is per-platform: Tauri's Webview::set_zoom maps to webkit2gtk set_zoom_level, WebView2
  SetZoomFactor and a WKWebView path on macOS, so user/app zoom changes the CSS-px-per-device-px
  ratio and layout must survive it (tie to WCAG 1.4.10 at 400% zoom):
  https://docs.rs/tauri/latest/tauri/webview/struct.Webview.html
- Linux fractional scaling: an open Tauri bug reports fonts/components rendering at a lower scale
  than expected on Ubuntu Wayland, with blur and pixelation obvious after zooming, and a reload
  fixing it temporarily - consistent with fractional DPR rounding/handshake:
  https://github.com/tauri-apps/tauri/issues/14590
- Practical implications: (a) minimum window size is a product decision, not a CSS detail; (b) canvas
  DPR math must round and re-read devicePixelRatio on scale changes; (c) test 125% and 150% Linux
  scaling plus macOS Retina; (d) system font/text scaling is a separate axis from CSS zoom and no
  authoritative doc was fetched for WebKitGTK system text scaling, so treat it as a manual test item.
- macOS WKWebView shares Safari's engine, so svh/dvh and container queries should be available on
  supported macOS versions (Safari supported dvh before Chrome 108 shipped, per the web.dev note);
  exact minimum OS versions are not established here - verify against the app's stated minimum macOS.

## Post-mortem read

Primary incident: WebKit Bug 209292, "CSS hover and pointer: fine media queries do not evaluate to
true with iOS 13.4 mouse support" (reported 2020-03-19 by Devon Govett, RESOLVED FIXED),
https://bugs.webkit.org/show_bug.cgi?id=209292 ; duplicate/related report 210024 (reported
2020-04-05, "iPadOS with mouse: interaction media features ... don't report mouse",
RESOLVED DUPLICATE of 209292): https://bugs.webkit.org/show_bug.cgi?id=210024

What happened: iOS/iPadOS 13.4 introduced external mouse and trackpad support. On those devices the
interaction media features did not reflect the newly available precision pointer: hover:hover and
pointer:fine stayed false, so pages that gate hover reveals, tooltips, or pointer-specific UI on
those queries kept serving the touch experience to a user who was pointing with a trackpad. The
report includes a reproduction against the MDN media-feature test page and screenshots.

Root cause: the engine's "primary pointing device" determination did not account for the iPad's
dynamically attachable pointer. Media Queries Level 4 leaves that determination to the UA and allows
it to change dynamically; WebKit had effectively cached the touch-first answer. The fix landed in
WebKit (bug RESOLVED FIXED); a later report (210024) shows the capability surface still being
corrected across configurations.

Lesson for Varve, in three parts:
1. Capability media queries are hints that can be wrong and can change at runtime (device attached or
   detached, OS version). Never let hover decide whether an action exists; let it decide only how the
   action is presented.
2. A tie between layout tier and input type is the failure mode: if "desktop layout" implies
   "hover available", the iPad gets desktop chrome it cannot operate. Tiering must be revisable when a
   pointer is attached.
3. The bug lived for months and shipped to users because it only reproduces on hardware with a
   specific accessory; emulated hover in DevTools cannot catch it. Real-device checks are part of the
   acceptance criteria, not optional QA.

Secondary evidence (data-quality incident, still open): MDN browser-compat-data issue 24451,
"css.at-rules.media.hover, css.at-rules.media.pointer - Inaccurate results on Android, ChromeOS,
Safari on iOS, Windows", https://github.com/mdn/browser-compat-data/issues/24451 - the issue quotes
the spec's expectation that primary-pointer determination combines device knowledge, number/type of
pointing devices, and current usage, and documents that real engines diverge. This is why the plan
should treat hover/pointer as enhancement signals with a keyboard/tap fallback, not as facts.

Related platform behavior change worth treating as an incident class: Safari 13 on iPad changed wide
pages with responsive meta tags to be scaled rather than horizontally scrolled
(https://developer.apple.com/documentation/safari-release-notes/safari-13-release-notes). A fixed-width
layout that "passes" on iPad may be scaled-to-fit, so visual QA on iPad must assert reflow (no page
scale) not just "nothing is cut off".

Honesty note: no corporate post-mortem of a responsive layout regression was found. Two search
rounds (8 queries) returned only SEO/AI-generated blog pages and unrelated incident tooling; those
were discarded rather than cited. The WebKit bug chain above is the verifiable incident writeup used
instead, and it is directly load-bearing for the plan's input-capability strategy.

## Prioritized risk list for Varve

Severity: P0 = will break ship on target devices; P1 = broken experience on 1+ target class;
P2 = quality/accessibility debt that compounds.

1. P0 - Desktop tier is hard-coded at 900 CSS px: minWidth 900 / minHeight 600 in
   apps/desktop/src-tauri/tauri.conf.json plus the 899px breakpoint (17 uses) means every sub-900 tier
   is untestable and unreachable in the desktop build. Areas: tauri.conf.json, Shell/shellStyles.css.
2. P0 - iPad tier misclassification. Width-only rules send a 1180x820 iPad to desktop in landscape
   and mobile in portrait; a 1366x1024 iPad always gets desktop. Areas: shellStyles.css, all
   @media (max-width: 899px) blocks, packages/editor/src/components/Shell, Menubar.
3. P1 - Unmanaged 900-1100 px band: no rule exists between 899 and the next breakpoint (900/980), so
   13-inch laptops at 125% scaling (~1093x614) and iPad Split View halves (~683) land in undefined
   layout. Areas: shell CSS, packages/home/src/home.css.
4. P1 - Left panels and inspector assume fixed widths and docked layout. Areas:
   packages/editor/src/components/LayersPanel/layers.css, VariablePanel.css,
   packages/editor/src/components/BrushBrowser/BrushBrowser.css, components/Settings/*.css.
5. P1 - Fixed/absolute chrome (19 CSS files with position: fixed): menubar, floating toolbar, context
   bar can cover the canvas on short viewports. Areas: Menubar.tsx, FloatingToolbar,
   ContextControlBar, shellStyles.css.
6. P1 - Hover-only affordances and tooltip-only actions. Areas: canvas overlays
   (CropOverlay, GradientHandleOverlay, AlignmentOverlay, CanvasOverlays), inspector rows, home
   file cards (FileCard.tsx, FileContextMenu.tsx).
7. P1 - Touch target sizes: toolbar/inspector icon buttons are below the 44 pt HIG target and may
   fail WCAG 2.5.8 spacing once rows get tighter on small screens. Areas: packages/ui/src/components,
   editor toolbar components, packages/home/src/BatchActions.tsx.
8. P1 - 100vh-based shells. Areas: shellStyles.css, apps/desktop/src/global.css,
   packages/home/src/home.css, modal/dialog CSS (CreateTableFromDataDialog.css, BatchBgRemoveDialog.css).
9. P1 - Dialogs and forms under the virtual keyboard. Areas: components/*Dialog.tsx, Settings tabs,
   Export dialogs, packages/home/src/BulkImportDialog.tsx, HomeSearchPalette.tsx.
10. P1 - Canvas touch gestures: drag selection, marquee, pan/zoom, two-finger gestures, pointercancel
    handling. Areas: packages/editor/src/canvas, tools/, hitTest/, CanvasArea.tsx, CanvasOverlays.tsx.
11. P2 - Tables/timeline horizontal overflow: a data table is a legitimate 2D-scroll exception under
    1.4.10, but it must be a scroll container, not page-wide overflow. Areas:
    CreateTableFromDataDialog.tsx/.css, timeline components, packages/home/src/FileList.tsx.
12. P2 - Home grid/cards not container-aware. Areas: packages/home/src/FileGrid.tsx, FileList.tsx,
    AssetBrowser.tsx, FolderView.tsx, home.css - candidates for @container.
13. P2 - Marketing site (Astro) has no documented phone/tablet contract. Areas:
    apps/website/src/layouts, apps/website/src/pages (about, compare, pricing, changelog),
    apps/website/src/styles.
14. P2 - Safe areas and install mode on web/PWA surfaces (website + any browser-served editor build).
    Areas: apps/website/src/layouts, index.html viewport metas, global CSS.
15. P2 - Tauri DPI/zoom correctness: fractional Linux scaling, user zoom, canvas devicePixelRatio
    rounding, min window size vs 1366x768 laptops. Areas: apps/desktop/src-tauri/tauri.conf.json,
    packages/compositor/src (canvas sizing), render worker setup in packages/editor/src/render.
